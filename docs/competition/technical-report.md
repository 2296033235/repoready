## 一、作品概述

### 1.1 背景与问题

开源项目的 README 会腐坏。依赖版本漂移、系统库缺失、CI 里实际执行的命令与文档描述脱节，这些腐坏在维护者自己的机器上不会显现——他的环境早就装好了。代价由两端承担：想提第一个 PR 的新人照着文档做到第二步就卡住，然后放弃；维护者收到"装不上"的 issue 时无从复现。

现有工具集中在**生成**文档这一侧，让 README 变多；没有人系统性地**验证**文档，让 README 变得可信。

> 待填：一到两个真实经历的简短记录（自己或同学照文档失败的案例），控制在 150 字内。规则允许"个人学习或项目实践记录"作为需求依据，不需要企业调研。

### 1.2 目标、参赛方向与作品形态

**目标**：给定一个开源仓库与一个 commit，自动产出**经过真实执行**的上手指南，每一步附带执行证据；失败时给出可定位、可分类、可执行的结论，而不是一句"安装失败"。

**参赛方向**：方向二「AI 开发工具与开源协作」。规则对该方向的定义是"面向代码开发、测试、文档、数据处理、知识管理、项目管理和开源社区协作等环节，形成提升效率或质量的智能工具、扩展组件和自动化流程"。本作品落在其中的**测试**与**文档**两个环节。

**作品形态**：命令行开发工具，附带可复现的评测套件与开放成果。

### 1.3 核心亮点

1. **结论由执行产生，不由模型生成。** 每一条"这一步能跑通"都对应一次真实执行，记录退出码、耗时与日志片段；模型的职责被限制在"失败归因"和"把结论翻译成人话"。
2. **证据必须可核验。** 归因结论引用的日志行必须能在该步骤自身的输出中原样找到，找不到就整条降级为"未知"。这条约束可当场演示。
3. **失败与阻塞分开统计。** 命令真的返回非零是"项目的问题"，环境不具备执行条件是"评测环境的问题"。混在一起，"可跑通率"就失去意义。
4. **零第三方运行时依赖。** 一个专治"装不上、跑不起来"的工具，自己必须 `git clone` 之后就能跑。每减少一个依赖，复现时就少一个失败点。

> 对应评分：创新性与方案设计（20 分）、AI 与开源融合（20 分）。亮点 1 与 2 是"AI 技术作用明确、必要"的直接论据。

## 二、需求分析与总体方案

### 2.1 需求分析

| 角色 | 现有做法 | 痛点 |
| --- | --- | --- |
| 新贡献者 | 照 README 手动执行，报错后搜索 | 不知道错在哪一步、为什么错，容易放弃 |
| 维护者 | 依赖自己的机器，或让提问者贴日志 | 无法复现，也说不清文档何时失效 |
| 教学与研究者 | 逐个仓库手工尝试 | 缺少可横向比较、可复现的数据 |

**需求优先级**：结论可信 > 覆盖广 > 速度快。本项目把可信放在第一位，宁可如实报告"这一步没跑成、原因是环境不具备"，也不给一个看起来漂亮但站不住的结论。

> 待填：可补充 1–2 条访谈或问卷结论（同学、社团、课程项目皆可）。

### 2.2 总体方案

三层单向数据流。**探测层只做静态分析、绝不执行仓库代码；执行层只执行、不判断；报告层只渲染、不重新判断。** 所有判断在执行层完成并写入 `run.json`，报告层不允许有自己的意见——这样报告与原始数据永远对得上。

```
     探测层 probe               执行层 runner             报告层 report
   ┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
   │ 项目识别          │   │ 后端协议          │   │ run.json（权威）  │
   │  语言与包管理器   │   │  docker（主）     │   │  每步一条记录     │
   │                   │   │  local（需显式）  │   │  含完整证据       │
   │ 步骤抽取（带出处）│──▶│                   │──▶│                   │
   │  CI 配置（最高）  │   │ 执行器状态机      │   │ report.md（人读） │
   │  文档代码块       │   │  首个失败即停止   │   │  步骤与出处       │
   │  清单文件推断     │   │  超时、资源上限   │   │  归因与建议       │
   │                   │   │                   │   │                   │
   │ 输出：Step 列表   │   │ 归因层            │   │ 输出：两份文件    │
   │ 每条带 文件+行号  │   │  七类固定分类     │   │                   │
   └───────────────────┘   │  证据校验闸门     │   └───────────────────┘
                           └───────────────────┘
```

**输入输出**：输入为仓库地址或本地路径、可选的 ref、后端与超时参数；输出为 `run.json`（权威数据）、`report.md`（人读报告）与每步的完整日志文件。

**运行流程**：统一克隆到临时目录并解析完整 commit → 识别项目类型 → 抽取步骤 → 逐步执行 → 归因 → 写报告。

### 2.3 可行性与成本

全部实现基于 Python 标准库，无需 GPU，无需训练模型，无需采购硬件。运行成本只有容器启动与依赖下载，可通过镜像缓存与超时上限控制。开发周期按两周安排，与在校学生的可支配时间相匹配。

## 三、AI 技术与开源及第三方资源选择

### 3.1 AI 技术作用

AI 在本作品中承担**理解与分类**，而不是生成内容：读取一个失败步骤的原始日志，判断它属于哪一类失败，并给出可执行的修复建议。

**为什么需要 AI**：失败日志的自然语言形态极其发散——同一个"缺系统库"的错误，在不同项目里有几十种写法。规则匹配能覆盖高频形态，覆盖不到的部分需要语义理解。

**如何验证 AI 输出**：这是本作品的差异化所在。归因结果必须同时满足三条才被采纳：

1. 分类必须落在七个固定类别之内；
2. 引用的每一条日志行都必须能在**该步骤自身的输出**中原样找到（比对前统一空白与换行，不做模糊匹配）；
3. 建议必须非空且在合理长度内。

任一条件不满足，整条归因降级为"未知"并标注"证据不足"。**模型可以说，但必须有据。**

> 对应评分：AI 与开源融合（20 分）。本节直接回答"AI 技术作用明确、必要"与"如何验证 AI 输出"。

### 3.2 开源及第三方资源选择

**运行时不依赖任何第三方 Python 包**——这是刻意的选型结果，不是偶然：

| 关注点 | 选择 | 选型依据 |
| --- | --- | --- |
| 命令行接口 | `argparse` | 标准库，避免为解析参数引入框架 |
| 数据模型 | `dataclasses` 加显式校验 | 校验逻辑显式可读，不依赖校验框架 |
| 模板 | `string.Template` | 报告模板简单，不值得引入模板引擎 |
| 配置 | JSON | 标准库可直接解析 |
| 容器调用 | `subprocess` 调用 docker 命令行 | 少一层绑定，且天然尊重 `DOCKER_HOST` |
| 测试 | `unittest` | 直接运行，无需安装 |

**第三方资源**：仅 Docker 作为外部运行时依赖，且为**可选**——缺失时降级到本地后端（需显式开启，见 7.5）。评测所用仓库均为公开项目，仅做只读克隆与本地执行，不修改、不转发其代码。

完整的资源清单见附录《开源及第三方资源使用清单》。

### 3.3 自主开发与权利边界

| 部分 | 来源 | 说明 |
| --- | --- | --- |
| 三层架构、数据模型、执行器、归因规则、证据闸门、报告渲染 | 团队自主设计开发 | 全部源代码在本作品仓库内 |
| Docker 引擎 | 第三方开源软件 | 仅作为外部运行时调用，未修改 |
| 评测所用的开源仓库 | 第三方 | 只读克隆，不修改、不再分发 |
| AI 辅助生成的代码与文本 | 通用 AI 工具 | 使用环节与人工审核见 4.3 |

### 3.4 融合方式

开源资源在本作品中不是"开发环境"，而是**被处理的对象**：作品的输入是开源仓库，输出是关于开源仓库的结论，产出的成果本身也以开源方式发布。AI 的作用是理解失败日志这一环节——没有 AI，规则匹配的覆盖率会成为瓶颈；没有证据闸门，AI 的输出不可信。两者互为约束，构成完整方案。

> 对应评分：AI 与开源融合（20 分）。规则要求说明"AI 技术与开源资源如何形成完整方案，而不是简单调用接口、直接部署项目或进行界面包装"。

## 四、设计与实现过程

### 4.1 核心功能与流程

**命令一：环境自检**

```
python -m repoready doctor
```

检查 Python 版本与 Docker 可用性，并把 Docker 的三种失败形态分开报告：命令行未安装、守护进程未运行、权限不足。三者的修复方式完全不同，笼统报"工具坏了"没有意义。

**命令二：验证单个仓库**

```
python -m repoready check <仓库地址或路径> --ref <commit> --out reports/<名称>
```

产出 `run.json`、`report.md` 与每步完整日志。

**关键设计约定**：被检查的项目失败时，工具自身的退出码仍是 0；项目的问题体现在 `run.json` 的步骤状态里。这条区分对批量评测至关重要——否则脚本会因为某个仓库失败而中断。

### 4.2 关键实现

**（1）步骤来源的优先级。** CI 配置排在文档之前，因为 CI 里的命令**正在被真实执行**，可信度高于文档描述。每条步骤记录来源类型、文件路径与行号，这是"可追溯"的基础。

> 待填：一张真实报告截图，展示同一仓库下 CI 来源与推断来源的步骤并列，且各自标出文件与行号。

**（2）命令级白名单。** 抽取时只接受以已知命令动词开头的行（`pip`、`python`、`pytest`、`make`、`poetry` 等）。这是开发过程中的一次关键修正：早期版本执行工作流里的**所有** `run:` 命令，对某个真实仓库抽取出的第一步竟是维护工作流里的关闭 issue 命令——工具产出的"上手指南"第一条指令是去关闭 issue。修正方案是把文档路径已有的命令白名单复用到 CI 路径，而不是再写一张需要同步维护的黑名单。

> 这是值得讲的工程故事：**用白名单而不是黑名单**，以及**同一个判断只允许有一处定义**。

**（3）失败分类与证据闸门。** 七个固定分类：缺系统依赖、版本冲突、需联网资源、需密钥、需 GPU、文档过时、未知。归因分两阶段——规则阶段离线覆盖高频形态，AI 阶段处理规则无法归类的情况，且必须通过 3.1 的三条校验。

**（4）执行隔离。** 容器后端为主：固定基础镜像、CPU 与内存上限、单步超时、能力裁剪、禁止提权、进程数限制、只读根文件系统。本地后端为降级选项，需显式开启，且**不继承宿主环境变量、默认无网络**。

### 4.3 团队分工与过程记录

> 待填：成员角色与时间计划。单人参赛则如实写明"单人完成"，并说明各阶段投入。

**生成式 AI 与智能体工具的使用说明**（规则第（七）条要求）

本作品在开发过程中使用了 AI 编码助手与多智能体工作流，用途与参与环节如下：

| 环节 | AI 参与方式 | 团队的审核、修改与验证 |
| --- | --- | --- |
| 需求与方案设计 | 辅助梳理与方案对比 | 团队确定技术选型与边界，逐条评审并裁定 |
| 代码实现 | 按任务分工生成代码与测试 | 每个任务先写失败测试、再写实现、跑通后提交 |
| 缺陷修复 | 辅助定位与修改 | 每个修复由独立审查者核验，并复跑覆盖测试 |
| 报告与文档 | 辅助组织语言 | 团队核对事实与数据，所有数字以工具实际产出为准 |

**关键的验证工作**：本作品的开发采用"实现—独立审查—修复—复审"的循环。每一次代码变更都由未参与该变更的审查者对照需求核验，并由团队对全部结论复跑测试。所有测试命令与输出均保留在仓库的审查记录中。

团队已对纳入作品的 AI 生成代码进行来源与权利核查：全部代码由团队在自有仓库内组织与修改，不包含从第三方复制的内容。使用的 AI 工具仅作为开发辅助，未在作品的运行时依赖中被调用。

## 七、合规、安全与风险说明

### 7.1 开源及第三方许可合规

本作品运行时仅依赖 Python 标准库与可选的 Docker，自身以开源许可证发布。完整清单见附录，逐项说明许可证类型、关键义务与合规状态。

### 7.2 数据、权利与隐私

作品不采集、不存储个人信息。评测所处理的仓库均为公开项目，仅做只读克隆与本地执行，不修改、不再分发其代码。执行产生的日志可能包含第三方项目的输出，报告在引用时只截取与失败归因相关的片段。

### 7.3 AI 输出、知识产权与内容安全

**幻觉风险**是 AI 归因的主要风险，应对方式是 3.1 的三条证据约束——这是本作品的设计重点，而不是事后补救。**提示注入**风险来自被检查仓库的日志内容，应对方式是归因结果必须通过证据校验，且校验只接受原样存在的日志行。

### 7.4 知识产权与公开边界

团队自主创作部分的代码与文档归团队所有；Docker 等第三方资源的知识产权归属不变。作品不包含受专利保护或商业秘密性质的内容。

### 7.5 其他风险与适用边界

- **在宿主机上执行陌生代码的风险。** 本地后端隔离性弱，因此被设计为**必须显式开启**，且在请求"无网络"时直接拒绝执行而不是静默放行。
- **容器执行超时的终止保证。** 在 Windows 上无法证明进程树已被完全终止，此时报告如实标记为"终止未确认"，而不宣称一个无法兑现的资源上限。
- **静态分析的性质。** 步骤抽取是启发式的，不是完整的 YAML 解析器，结构异常的工程文件可能被漏读。工具选择"宁可漏读、不可虚构"。
